# Coverage assets: design

The coverage matrix is generated, committed, and diffed on every push, so a
coverage change shows up in review. That choice has a cost that grew with the
matrix. `docs/coverage/matrix.json` lists 745 test names, so any PR that adds,
renames, or deletes a test changes it, and two PRs that each add a test
conflict on it. Regenerating it needs Docker and the full release suite. Of
the last 60 CI runs, 23 failed, and 19 of those failed only on "the coverage
matrix is out of date" with every suite green.

This design keeps the review signal and drops the churn. The committed
artifact becomes the set of statuses the gate judges, one small file per
integration. Everything else the matrix knows moves to a report that CI
publishes on every run. Two further steps split the largest registry and the
generator along the same lines, so an agent changing one integration or one
concern of the generator loads one small file.

## Why now

Counted on 2026-09-10, on `main` at cc4f088:

- 60 most recent CI runs: 37 passed, 23 failed. 19 of the 23 failed on the
  stale-matrix check alone. 4 failed on a test.
- 40 most recent commits: 18 changed `matrix.json` and `matrix.md`. 15 of
  those share the current format. All 15 changed per-cell test-name lists,
  5 changed nothing else, and 2 changed the unattributed list.
- `matrix.json` is 4091 lines, about 36k tokens. It is what an agent opens to
  resolve a conflict, and no judgement goes into that resolution, because the
  file is derived.
- `integrations.yml` is 602 lines. ClickHouse's entry is 369 of them, nearly
  all its type table. Every other integration is 5 to 50 lines.
- `scripts/coverage_matrix.py` is 1218 lines and its test file is 1820.
  Changing the generator means loading about 32k tokens.
- The maintainer's clone has 24 worktrees and 113 branches. Concurrent
  branches are the normal case, not the exception.

The merge driver in `.gitattributes` does not help on GitHub, which never
runs it, so the PR page shows a conflict regardless.

## Goals

1. A PR that adds tests inside already-covered features changes nothing under
   `docs/coverage`. It passes CI on its first run and cannot conflict on a
   generated file.
2. An agent working on one integration, or on one concern of the generator,
   loads one small file for it. No committed coverage asset exceeds about 5k
   tokens, and no generator module exceeds 300 lines.

## Decisions

| Decision | Choice | Rejected |
|---|---|---|
| What is committed | The statuses the gate judges: one per (feature, level) and one per (invariant, integration, level). | The full snapshot with test names (today). Nothing, with the gate in CI only: a status flip would no longer appear in review. |
| Partition | One file for features. One file per integration for invariants. | One file: two PRs flipping different integrations would still conflict. One file per family: a PR about one integration would touch five files. |
| Format | YAML. One row per line, rows sorted by id, levels in a flow mapping in `unit, integration, release` order. | JSON: indentation spreads one fact over five lines, and git merges lines. |
| The page | Stays committed. Rendered from the status files and registries alone, so anyone regenerates it without Docker and the Tooling job checks it in seconds. | Rendered from test reports (today). Not committed: the README's entry point would go. |
| Detail | A report CI appends to the job summary and uploads on every run: counts, names, by-marker, unattributed, unknown markers. | Uploaded on failure only (today). |
| Unknown markers | Fail the gate. | Listed on the page (today). Once the list leaves the reviewed diff, nobody reads it. |
| Merge driver | Kept for `matrix.md`, which `make coverage-page` regenerates. Removed for the status files, which git merges line by line. | A driver on the status files: "keep ours" would discard a status flip from `main` that only CI could restore. |
| Registries | `integrations.yml` splits per integration. `features.yml`, `invariants.yml`, and `lattice.yml` stay whole. | Splitting everything: the whole files are under 3k tokens each, and a new invariant is one edit in one place. |
| Generator | A package with one module per concern and a test file per module, behind the existing `scripts/coverage_matrix.py` entry point. | One file (today). |

## The committed artifact

### Status files

`docs/coverage/status/features.yml` holds one line per feature in
`features.yml`:

```yaml
# Generated by `make coverage-matrix`. Do not edit by hand.
# One line per feature in ../features.yml, sorted by id: the status of each level.
cli.dev_invoke: {unit: covered, integration: not_required, release: covered}
cli.invocation: {unit: covered, integration: not_required, release: not_required}
```

`docs/coverage/status/<integration>.yml` holds one line per invariant that
applies to that integration. A file exists for every registry entry that is
not `test_only` and has at least one applicable invariant. Pipeline
configurations are integrations here, as they are in the registry:

```yaml
# Generated by `make coverage-matrix`. Do not edit by hand.
# One line per invariant that applies to sink.clickhouse, sorted by id: the status of each level.
sink.batch.keeps_batch: {unit: covered, integration: covered, release: missing}
sink.error.classifies: {unit: exempt, integration: exempt, release: exempt}
```

The vocabulary is today's. A feature level is `covered`, `skipped`,
`missing`, `failing`, or `not_required`. An invariant cell is `covered`,
`skipped`, `missing`, `failing`, or `exempt`. The meanings do not change: a
level is `covered` only if a test ran there and passed. An `exempt` row
repeats what the integration's registry entry declares, so a reader of one
file sees the whole picture for that integration. The generator writes it
from the registry, so the two cannot disagree.

Today's tree produces 36 feature rows and 130 invariant rows across 11
integration files, about 170 lines in all. Handlers have no invariants yet,
so they have no file.

Nothing else from a test run is committed. A gap derives from a status row
and the registry's `requires`, so the page renders gaps and no list of them
is stored.

### What leaves git

`docs/coverage/matrix.json` is deleted from the tree. The generator still
builds the full snapshot in memory, because the gate judges gaps from it, and
writes it unchanged to `.coverage/matrix.json`, which is already ignored.
Test names, counts, skipped and failing lists, by-marker lists, and
unattributed tests live there and in the report.

### The page

`docs/coverage/matrix.md` stays, so the README's link holds. It renders from
the status files and the four registries, and from nothing else. `make
coverage-page` renders it with no test report present, which is how a
conflict on it is resolved after a merge.

The page keeps: the feature table without the Tests column, the totals
sentence, the invariant tally with the safety and liveness paragraph, the
invariant tables, Gaps, and Invariant gaps. It drops the sections built from
names and counts: "Why invariants, and not the test count", "Covered only by
another test's marker", "Unattributed unit tests", and both unknown-marker
sections. Its header names `docs/coverage/status/` and `make coverage-page`
instead of `matrix.json`. The sentence "exempt carries its reason in the
JSON" points at `integrations.yml`, where the reason is declared.

### The report

`.coverage/report.md` holds what the page dropped: the feature table with a
test count per level, the argument that pairs the most-tested feature with
the least-proven invariant, covered-only-by-marker, unattributed tests per
level, and unknown markers. `make coverage-check` prints it. CI appends it to
`$GITHUB_STEP_SUMMARY` and uploads it with `.coverage/matrix.json` and the
regenerated `docs/coverage` files as the `coverage-report` artifact on every
run, `if: always()`.

### The gate

`make coverage-check` keeps its three parts and their order: gaps, suite
failures, then staleness. Two changes:

- A marker naming an unknown feature, invariant, or integration is a gap. It
  fails `--check` and the log names the test and the id.
- The staleness diff covers `docs/coverage/status/`,
  `docs/coverage/matrix.md`, and `docs/coverage/clickhouse-types.mdx`.

The log already prints the diff when staleness fails. A status flip is one
line in one file, which a contributor applies by hand.

The Tooling job gains a check that needs no test report: the committed page
equals the page rendered from the committed status files and registries. A
stale page fails in seconds, before any suite runs.

### Makefile, CI, and git

- `coverage-write` writes the status directory, the page, the types page,
  `.coverage/matrix.json`, and `.coverage/report.md`.
- `coverage-page` renders the page and the types page from committed files.
  It reads no report.
- `coverage-check` as above.
- `.gitattributes` names `docs/coverage/matrix.md` only. Its comment says
  what to run after a merge.
- The coverage job in `ci.yml` appends the report to the job summary and
  uploads the artifact on every run.

### Tests

The tooling tests that assert names and counts on the page move to the
report renderer. New tests, each a pure function of in-memory inputs unless
stated:

1. Adding a passing test to a feature already covered at that level leaves
   every status file byte-identical.
2. A test with no marker reaches the report and no status file.
3. A status flip changes exactly one line in exactly one file.
4. The page renders from status files and registries with no test report.
5. The committed page equals the rendered page. Reads the repo. Runs in the
   Tooling job.
6. An unknown marker makes `--check` exit non-zero.
7. An exempt row in a status file matches the registry's exemption.

`test_no_committed_invariant_is_unwired` reads the status directory instead
of `matrix.json`.

## Registries per integration

`docs/coverage/integrations.yml` becomes `docs/coverage/integrations/<id>.yml`,
one file per entry. Each file is the entry's mapping with its `id` inside it.
A file whose name and `id` disagree fails `validate_registries`. The header
comment moves to `docs/coverage/integrations/README.md`. Order is by id,
which fixes the column order on the page.

Loaders:

- Python: `load_integrations()` reads every `*.yml` in the directory, sorted
  by name, and returns the list the single file returned.
- Go: every function in `internal/coverage/registry.go` that calls
  `readRegistry("integrations.yml")` shares one loader that reads the
  directory and returns the same slice. The `Kinds()` agreement tests in
  `internal/sinks`, `internal/sources`, and `internal/handlers` do not
  change.

The status directory mirrors this layout, so everything about
`sink.clickhouse` is two files: its declaration and its status.

## Generator as a package

`scripts/coverage_matrix.py` becomes the entry point of
`scripts/coverage_matrix/`, a package with one module per concern:

| Module | Holds today's |
|---|---|
| `registries.py` | `load_*`, `validate_registries`, the constants |
| `reports.py` | `parse_go`, `parse_pytest` |
| `features.py` | `build`, `snapshot`, `status` |
| `invariants.py` | `build_invariants`, `snapshot_invariants`, `cell_state`, `invariant_tally` |
| `status.py` | writing and reading the status directory |
| `page.py` | the page renderer |
| `report.py` | the report renderer, `strongest_argument` and its helpers |
| `types.py` | `validate_types`, `render_types_page` |
| `cli.py` | `main` |

The entry point puts its directory on `sys.path` and calls `cli.main`, so the
Makefile does not change. `tests/tooling/test_coverage_matrix.py` splits into
one file per module. No module exceeds 300 lines. An agent changing one
concern loads that module and its tests.

## Rollout

Three PRs, each mergeable on its own, in blast-radius order.

### PR 1: statuses only

Everything under "The committed artifact". Done when a PR that adds a test to
a covered feature produces no diff under `docs/coverage`, the coverage job
passes on it, and the tooling suite holds the seven tests above.

### PR 2: integrations per file

Everything under "Registries per integration". Done when both loaders read
the directory, the page and the types page are byte-identical to before the
split, and `validate_registries` rejects a misnamed file.

### PR 3: the generator as a package

Everything under "Generator as a package". A move, not a rewrite. The page,
the report, the status files, and the types page are byte-identical before
and after.

### After

- The merge driver can go once page conflicts stop being reported.
- The report can publish to GitHub Pages if a stable URL for names and counts
  turns out to matter. Nothing asks for one yet.

## Out of scope

- The conformance harness. `internal/conformance` is 154KB, about 38k
  tokens, and an invariant PR still loads it. That is a separate
  decomposition.
- A bot that commits regenerated files to a PR branch.
- What the gate judges. Gaps and suite failures fail the build exactly as
  they do today. Unknown markers are the only addition.
- The `docs/superpowers` plans that name `matrix.json` in their `git add`
  lines. They record what was done.
