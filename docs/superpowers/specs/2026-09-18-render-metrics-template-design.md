# Deploy to Render: a metrics pipeline from one button, and the install telemetry it reports

No issue yet. Verified against `main` at bc86bc7 on 2026-09-18. The Render
facts under "The Blueprint" were read from Render's Blueprint reference and
Deploy to Render page on 2026-09-18.

This is the umbrella spec. It fixes the scope, the decisions, and the build
order. Two engine changes it depends on have their own specs:

- [Webhook listen address](2026-09-18-webhook-addr-design.md)
- [Rollup: non-integer sums and a `last` measure](2026-09-18-rollup-double-and-last-design.md)

## The problem

sqlflow's README shows pipelines a reader runs locally. Nothing takes a
reader from the README to a running pipeline they can send data to and query
back. The Bluesky demo has a Deploy to Render button, but it lives in another
repository, reads a firehose the user does not own, and accepts no input.

This spec adds a button to the sql-flow README. One click creates a Postgres,
a pipeline that accepts metrics over a signed webhook and aggregates them by
minute, and an HTTP API that reads them back. Five minutes after the click, a
user has sent a `curl` and queried its result.

The same template reports two install events to a collector we run. The
collector is the same template, deployed from the same button, with signature
validation switched off.

## Scope

In:

- A `render.yaml` at the repository root and a `/render` directory holding
  every other asset of the template.
- A generic metric: a name, a type (`count` or `gauge`), a value, a flat set
  of string dimensions, and an optional timestamp.
- A one-minute tumbling window written to Postgres through the `postgres`
  sink, and a six-grain rollup ladder generated by `sqlflow rollup`.
- Two serve datasets: the series seen, and one metric over a time range.
- HMAC validation on by default, prompted for at deploy, and a pipeline that
  refuses to start without a secret.
- An explicit switch that turns validation off, so one template serves both
  users and our collector.
- Install telemetry: an install ID, two events, on by default, prompted for
  at deploy, disclosed in the README.
- CI that brings the template up, sends a signed request, and reads it back.

Out, each a follow-up:

- Filtering by some dimensions and summing across the rest. It needs either
  aggregation pushdown, which the DuckDB postgres extension lacks, or a
  rollup per dimension.
- Backfill. A metric whose timestamp is older than the open windows is
  dropped.
- Per-row validation errors in the webhook response. The source acknowledges
  a request before the handler reads it.
- Histograms and percentiles.
- Retention on the minute table.
- A chart page.

## Decisions

Made in the design conversation on 2026-09-18. Each one closes a fork.

| Decision | Choice | Rejected |
|---|---|---|
| Where the template lives | The sql-flow repository: `render.yaml` at the root, all other assets in `/render`. | A dedicated repository, as the Bluesky demo is. The button belongs beside the engine it deploys. |
| Why one file is at the root | Render's button documents one parameter, `repo`, and reads `render.yaml` from the root. A custom Blueprint path exists only in the dashboard's manual flow. If a test shows the button honors a subdirectory, `render.yaml` moves into `/render`. | Assuming the subdirectory works. |
| Blank HMAC secret | The entrypoint exits 2 and names the variable. | Starting unsigned with a warning: a public write endpoint into the user's Postgres. Generating a secret and logging it: a secret in logs. |
| Unsigned mode | `SQLFLOW_WEBHOOK_AUTH=none`, set on purpose. The config's `{% if %}` omits `signature_type`. | A second template for the collector. A blank secret meaning unsigned. |
| What a minute stores | `sum`, `count`, `min`, `max`, `last`, for both types. | `last` only: a spike inside a minute vanishes and no average exists. `avg`: an average of averages is wrong at every coarser grain. |
| `last` at launch | Ships. | Adding it later. Deployed copies do not redeploy themselves, so the launch schema is the schema. |
| Rollups at launch | The full ladder, 1m through 1d. | The minute table alone. Our collector needs multi-day ranges within a week of launch. |
| Dimension filter | Exact match on the whole dimension set, through a canonical text key. Text equality pushes down to Postgres. | `jsonb` containment, which DuckDB would evaluate after pulling the range. |
| Telemetry consent | On by default, opt out with one variable, prompted for at deploy, payload listed in the README. | Opt-in: counts too low to use. No opt-out: not acceptable for open-source infrastructure. |
| Where telemetry code lives | Shell in `/render/bin`. The sqlflow binary sends nothing. | Telemetry in the engine. |
| The collector | The public button, deployed in our workspace from the template's PR branch, with three variables set. | A private repository with its own code. One is needed only to keep saved queries. |
| Late rows | `late_rows: drop`. | `reemit`. The sink replaces a key rather than merging into it, and `sqlflow validate` refuses the pair. |

## Layout

```
render.yaml                   the Blueprint; points into render/
render/
  Dockerfile                  FROM turbolytics/sql-flow:<pinned tag>, plus postgresql-client and curl
  pipeline.yml                webhook source, handler, window, postgres sink
  serve.yml                   commands, server, and the series and metric datasets, written by hand
  rollups.yml                 the ladder; no serve block
  migrations/                 0001_metrics.sql, 0002_series.sql, 0003_install.sql, 0004_rollups.sql (generated)
  bin/entrypoint.sh           checks, migrate, telemetry, exec sqlflow run
  bin/serve.sh                checks, exec sqlflow serve
  bin/migrate.sh              as the Bluesky demo's, including the wait for the database
  bin/telemetry.sh            the two events
  bin/send.sh                 signs and posts a metric; the README's first request
  docker-compose.yml          Postgres, pipeline, serve; the local run and the CI run
  Makefile                    validate, rollups, up, test
  README.md                   the contract, the prompts, what telemetry sends
```

The image is built `FROM` a published sqlflow tag, as the Bluesky demo's is.
Render does not compile Go or fetch DuckDB. The tag must contain both engine
changes, so the template lands after a release.

## The Blueprint

One database and two web services, in one region, because
`connectionString` is the private-network URL.

| Resource | Type | Notes |
|---|---|---|
| `sqlflow-metrics-db` | Postgres | `0.1c-256mb`, 5 GB, autoscaling off. |
| `sqlflow-metrics-ingest` | web | `dockerfilePath: ./render/Dockerfile`, `dockerContext: ./render`. Public `POST /events`. |
| `sqlflow-metrics-api` | web | Same image, `dockerCommand: /app/bin/serve.sh`. `healthCheckPath: /healthz`. |

Both services set `autoDeployTrigger: "off"`. A copy in a user's workspace
must not redeploy when sql-flow's `main` moves.

The ingest service is a web service, not a worker, because only a web service
gets a public URL. The webhook source has no health route; whether Render
needs one for a web service without `healthCheckPath` is checked in the first
deploy, and if it does, `GET /healthz` joins the webhook address spec.

Environment variables on the ingest service:

| Key | Source | Meaning |
|---|---|---|
| `SQLFLOW_POSTGRES_URI` | `fromDatabase` | Private connection string. |
| `SQLFLOW_WEBHOOK_HMAC_SECRET` | `sync: false` | Prompted at deploy. Blank fails the deploy unless auth is `none`. |
| `SQLFLOW_TELEMETRY` | `sync: false` | Prompted at deploy. Blank means on. `off` disables it. |
| `SQLFLOW_WEBHOOK_AUTH` | `value: hmac` | `hmac` or `none`. |
| `SQLFLOW_WEBHOOK_PORT`, `PORT` | `value: "8001"` | The listener and what Render routes to. |
| `SQLFLOW_WEBHOOK_MAX_BODY_BYTES` | unset | Default 25 MiB. |
| `SQLFLOW_METRIC_NAME_PREFIX` | unset | When set, only names with this prefix are kept. |

Render's reference says of `sync: false`: "During the initial Blueprint
creation flow in the Render Dashboard, you're prompted to provide a value."
It prompts with the key alone, so the README lists each prompt and what to
type, directly above the button.

The API service takes `SQLFLOW_POSTGRES_URI`, a `generateValue` client id,
and its port, as the Bluesky demo does.

## The metric

A request body is one metric or an array of metrics.

```json
{
  "name": "checkout.completed",
  "type": "count",
  "value": 1,
  "dimensions": {"region": "us-east", "plan": "pro"},
  "timestamp": "2026-09-18T14:03:22Z"
}
```

| Field | Required | Default | Rule |
|---|---|---|---|
| `name` | yes | | Non-empty string, at most 200 bytes. |
| `type` | yes | | `count` or `gauge`. |
| `value` | no | `1` | A number. |
| `dimensions` | no | `{}` | A flat object, at most 16 keys. Values are read as strings. |
| `timestamp` | no | arrival time | RFC 3339. |

The handler's SQL keeps a row that meets every rule and drops the rest. A
dropped row is counted in a Prometheus counter and the request still answers
200, because the source acknowledges before the handler runs.

`dimensions_key` is the canonical form of `dimensions`: keys sorted, rendered
as compact JSON. `{"a":"1","b":"2"}` and `{"b":"2","a":"1"}` are one series.

`type` selects nothing in storage. It tells the read API which column is the
metric's headline value: `sum` for a count, `last` for a gauge.

## The window

As the Bluesky demo's: `size_seconds: 60`, `grace_seconds: 60`,
`idle_close_seconds: 60`, `late_rows: drop`, `poll_interval_seconds: 10`.

The in-memory table holds one row per batch per key, carrying `value_sum`,
`value_count`, `value_min`, `value_max`, `value_last`, and `last_at`.
`emit_sql` merges a closed minute's rows: sums, `min`, `max`, and
`arg_max(value_last, last_at)`.

A first `curl` reaches Postgres after the batch flushes and the minute
closes: up to about two minutes. The README says so beside the first request.

## Storage

`metrics_1m`, written by the sink with `mode: upsert`:

| Column | Type |
|---|---|
| `bucket` | `timestamptz` |
| `name` | `text` |
| `type` | `text` |
| `dimensions_key` | `text` |
| `dimensions` | `jsonb` |
| `value_sum`, `value_min`, `value_max`, `value_last` | `double precision` |
| `value_count` | `bigint` |
| `last_at` | `timestamptz` |
| `updated_at` | `timestamptz DEFAULT now()` |

The primary key is `(bucket, name, type, dimensions_key)`.

`series` holds one row per `(name, type, dimensions_key)` with `dimensions`,
`first_bucket`, and `last_bucket`. A statement-level trigger on `metrics_1m`
upserts it in the sink's transaction. Rollup tables carry `dimensions_key`
and never `jsonb`; `series` is where a key turns back into dimensions.

`install` holds one row: `install_id uuid DEFAULT gen_random_uuid()`,
`deployed_sent_at`, `first_request_sent_at`.

`rollups.yml` declares one rollup over `metrics_1m` with grains 5m, 15m, 1h,
6h, 1d, dimensions `[name, type, dimensions_key]`, and measures:

```yaml
measures:
  value_sum:   {type: sum, column: value_sum, numeric: double}
  value_count: {type: sum, column: value_count}
  value_min:   {type: min, column: value_min}
  value_max:   {type: max, column: value_max}
  value_last:  {type: last, column: value_last}
```

`numeric: double` and `type: last` are the rollup spec's two additions.
`make validate` runs `sqlflow rollup check` and fails when the migration has
drifted.

The declaration has no `serve:` block. `sqlflow rollup` serves a dataset of
at most one dimension, folded, and this one has three and cannot fold. The
`metric` dataset's six grains are written by hand in `serve.yml`, each a
filtered select over `metrics_1m` or one generated table. Nothing checks them
against the declaration, so the CI test below queries every grain.

## The read API

The Bluesky demo's contract: `?client_id=` on every route except `/healthz`
and `/metrics`.

| Route | Returns |
|---|---|
| `GET /v1/datasets/series` | Every series seen: name, type, dimensions, first and last bucket. |
| `GET /v1/datasets/metric?name=…` | Per bucket and series: `sum`, `count`, `min`, `max`, `last`. |

`metric` takes `name` (required), `since`, `until`, `grain`, and
`dimensions`. `dimensions` is a JSON object; the request matches the one
series whose `dimensions_key` equals its canonical form. Without it, every
series of the name returns.

Canonicalizing a request's `dimensions` happens in the dataset's SQL with
DuckDB's JSON functions, over a bound parameter. If that cannot be written to
match the handler's form byte for byte, the param becomes `dimensions_key`
and the README shows the canonical form. The plan settles this with a test
before building on it.

Grains and their widest ranges are the Bluesky demo's: 1m to 6h, 5m to 1d,
15m to 3d, 1h to 14d, 6h to 90d, 1d to 365d.

## Signature validation

`pipeline.yml` renders the webhook block through Jinja2, which the config
loader already does:

```yaml
    webhook:
      addr: "0.0.0.0:{{ SQLFLOW_WEBHOOK_PORT|default('8001') }}"
      max_body_bytes: {{ SQLFLOW_WEBHOOK_MAX_BODY_BYTES|default('26214400') }}
{% if SQLFLOW_WEBHOOK_AUTH|default('hmac') == 'hmac' %}
      signature_type: hmac
      hmac:
        header: X-Signature-256
        secret: "{{ SQLFLOW_WEBHOOK_HMAC_SECRET }}"
{% endif %}
```

`entrypoint.sh` decides before sqlflow starts:

| `SQLFLOW_WEBHOOK_AUTH` | Secret | Result |
|---|---|---|
| `hmac`, or unset | set | Starts signed. |
| `hmac`, or unset | blank | Exits 2: `SQLFLOW_WEBHOOK_HMAC_SECRET is not set`. |
| `none` | ignored | Starts. Logs `webhook accepts unsigned requests`. |
| anything else | | Exits 2 and names the two values. |

Unsigned mode is never reached by omission.

`bin/send.sh` and the README show the signed request:

```sh
body='{"name":"hello","type":"count"}'
sig=$(printf '%s' "$body" | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //')
curl -X POST "$URL/events" -H "X-Signature-256: sha256=$sig" -d "$body"
```

## Telemetry

Two events, each sent once per install, each an ordinary metric posted to our
collector's `/events`:

```json
{"name": "install.deployed", "type": "count", "value": 1,
 "dimensions": {"install_id": "<uuid>", "sqlflow_version": "<tag>", "template": "render-metrics"}}
```

| Event | Sent when | Recorded in |
|---|---|---|
| `install.deployed` | Migrations succeed and `deployed_sent_at` is null. | `install.deployed_sent_at` |
| `install.first_request` | `metrics_1m` has its first row and `first_request_sent_at` is null. | `install.first_request_sent_at` |

`telemetry.sh` runs in the background from the entrypoint. It sends the first
event, polls for the second every 30 seconds, sends it, and exits. Each send
is `curl --max-time 5`, and a failure is retried on the next start, never in
a loop. A collector that is down changes nothing about the user's deploy.

The install ID names a database. The payload carries nothing else: no
hostname, no metric names, no counts, no Render identifiers. The README's
"What this sends" section prints both payloads in full and the one variable
that stops them. The entrypoint logs one line when it sends.

`SQLFLOW_TELEMETRY=off` skips `telemetry.sh` entirely. The collector URL is a
constant in `telemetry.sh`, overridable by `SQLFLOW_TELEMETRY_URL` for tests.

## The collector

The button, deployed in our workspace from the template's PR branch
(`?repo=…/tree/<branch>`), which is also the template's first real deploy.
Three variables differ from a user's copy:

| Key | Value | Why |
|---|---|---|
| `SQLFLOW_WEBHOOK_AUTH` | `none` | An install has no secret to sign with. Anything shipped in a public repository is not one. |
| `SQLFLOW_METRIC_NAME_PREFIX` | `install.` | Drops everything that is not an install event. |
| `SQLFLOW_WEBHOOK_MAX_BODY_BYTES` | a few KB | An install event is under 300 bytes. |

The endpoint is open, so its counts are approximate and the README for our
own use says so. The collector leaves its own telemetry on: its own
`install.deployed` arriving is the end-to-end check.

## Testing

- The two engine changes: unit and golden tests, in their own specs.
- `make -C render validate`: `sqlflow validate` on both configs, `sqlflow
  rollup check`, and `render.yaml` against Render's JSON schema.
- `make -C render test`, run in CI: compose up, apply migrations twice, post
  a signed metric, a gauge with a fraction, an array, and one bad row; wait
  for the window; assert the `series` response and the `metric` response at
  each of the six grains, that `0.73` came back as `0.73`, that the bad row is absent, and that the two
  dimension orders are one series.
- Auth: an unsigned request is refused under `hmac`; the entrypoint exits 2
  on a blank secret; `none` accepts an unsigned request.
- Telemetry: a second compose instance as the collector. Each event arrives
  once across a restart; `off` sends nothing; a dead collector does not fail
  the entrypoint.
- One manual deploy from the PR branch, which becomes the collector. It
  records the ingest service's resident memory for the README.
