# `sqlflow rollup run`: SQLFlow manages the rollups the database keeps

`sqlflow rollup run` is a daemon that manages the rollup tables a
`rollups.yml` declares. It installs and upgrades their tables and triggers,
backfills them in chunks, checks every table against the table it is built
from, and reports freshness, completeness and drift through `/metrics`,
`/healthz` and TurboStats. The triggers still do the merge: on Postgres they
are the cheapest way to keep a rollup current. `sqlflow rollup test` checks a
declaration against fixtures and generated writes on a real Postgres in CI.

The declaration, the generated SQL and the pipeline do not change. What
changes is who applies the SQL, and what SQLFlow knows about it afterward.

## The problem

`sqlflow rollup ddl` prints a migration, and the team applies it. After that,
SQLFlow knows nothing about the rollups:

- The team owns the generated PL/pgSQL, 432 lines in
  `sql-flow-bluesky-demo/migrations/0005_rollups.sql`, and regenerates and
  reapplies it for every change.
- The migration's backfill holds `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE`
  on the source for its whole run, so the pipeline's writes wait on the
  history. The 2026-09-15 spec left chunked backfill out of scope.
- Nothing reports whether a rollup is correct. A disabled trigger, a hand edit
  or a writer that bypasses the triggers leaves wrong totals that nobody sees.
- Nothing reports freshness where the data landed. A pipeline that runs and
  writes nothing looks healthy from the pipeline's own report.

Metering is the first market for this work. A billing total that is silently
wrong is the one failure a metering customer cannot accept, and a rollup
nobody checks is how it happens.

## Scope

In:

- `sqlflow rollup run`, `install`, `verify` and `test`.
- The state table, the reconcile planner, and chunked backfill.
- A freshness package that measures a table, and a store identity that is the
  same for every reporter.
- A top-level `freshness` list and a `rollup` section in the TurboStats
  bundle.
- `/metrics` and `/healthz` for the daemon.
- `store` and `turbostats` blocks in `rollups.yml`.
- Adopting the daemon in `sql-flow-bluesky-demo` and in the Render template
  in this repository.

Out, each with its own spec:

- A strategy where the daemon does the merge, for raw events. See
  "Follow-ups" for what is already measured.
- ClickHouse incremental materialized views.
- `sqlflow monitor`, a second reporter of the `freshness` list.
- Control's freshness view.
- Dropping a removed table, adding a measure to an existing dimension set,
  and retention.
- Renaming `sqlflow rollup serve`, or serve reading `rollups.yml` directly.

## Depends on

- Postgres 15 or later, as the 2026-09-15 spec already requires.
- A direct or session-pooled connection. The leader lock is a session
  advisory lock, which a transaction-pooling proxy such as PgBouncer in
  transaction mode releases between statements.

## Decisions

| Decision | Choice | Rejected |
|---|---|---|
| What does the merge on Postgres | The triggers the generator writes today, with a lock per rollup so writers take turns. A statement trigger re-merges the buckets one write touched, in the writer's transaction, with no lag and no change cursor. Both v1 sources write each closed minute once, so each bucket re-merges about once a minute. | The daemon re-merging on a schedule. It needs a change column, an index that every write maintains, and a tick of lag, to do the same re-merge. It wins only when many statements write one bucket, which is raw metering events, and it ships with them. `REFRESH MATERIALIZED VIEW`: it reruns the full query on every refresh, so its cost grows with history. Logical decoding: it needs `wal_level=logical` and a replication slot, which keeps WAL while the daemon is down, on the demo's 5 GB disk. |
| What SQLFlow owns | Everything around the merge: the objects, backfill, verify, reporting and tests. | Leaving it to the team's migrations, which is today's design and the problem above. |
| Where the daemon runs | Its own process, `sqlflow rollup run`. A slow backfill never delays the pipeline or the API. | Inside `sqlflow run`: it shares the pipeline's memory and failure domain. Both hosts: two wiring paths to test. |
| Who creates rollup tables | The daemon, and `sqlflow rollup install` for deploy scripts that must create them before `sqlflow serve` prepares its statements. | Team migrations generated by `rollup ddl`. `ddl` stays for a team that applies SQL itself. |
| Two daemons at once | Correctness never depends on the leader lock. Installs serialize behind a transaction lock, and backfill and verify are safe to run twice. The leader lock only keeps one daemon doing the work. | A leader lock that correctness depends on. A network partition leaves two leaders until Postgres notices the dead session. |
| A declaration change | Additive changes apply. A removed rollup, grain or dimension set keeps its tables and triggers, logs a warning, and stays under verify. A change that would corrupt stored rows stops the daemon with the change named. | Refusing removals: rolling back to the previous `rollups.yml` would then fail every entrypoint that runs `install`, the API's included. Dropping removed tables: a typo would delete history. |
| Backfill | Chunks of one source day, newest first, one transaction each, under the triggers' own per-bucket locks, after the triggers exist. | The migration's single transaction under `LOCK TABLE`: the pipeline waits for the whole history, and a long history exhausts the lock table unless the locks are skipped. |
| Freshness | A top-level bundle list keyed by store and table, which any process can report. | Inside the `rollup` section: Control could not show a table's freshness apart from the process that reported it. |
| CI tests | `sqlflow rollup test` against a real Postgres. | Embedded DuckDB: it tests a second dialect, not the SQL production runs. |
| Configuration | `store` and `turbostats`. Intervals are constants. | Knobs before anyone has measured a need for one. |

## Maintain and manage

A rollup needs two jobs done:

- **Maintain**: the merge itself. Each store uses its most efficient
  mechanism.
- **Manage**: everything around the merge. The daemon does this on every
  store.

| Mechanism | Where the merge runs | Cost grows with | Lag | Fits |
|---|---|---|---|---|
| Postgres trigger | The writer's transaction | Write statements | None | Sources written once per closed window: the Bluesky demo, the Render template |
| Postgres materialized view | `REFRESH` on a schedule | The whole history, every refresh | The interval plus the refresh | Small, bounded tables |
| ClickHouse incremental materialized view | ClickHouse, on insert | Inserted rows | None | Insert-only sources with deduplicated inserts |
| Daemon re-merge | The daemon, each tick | Buckets changed per tick | One tick | Raw events with many writes per bucket; stores with no mechanism, such as Iceberg |

v1 has one strategy, `trigger`, on one store, Postgres. When the daemon is
down, the rollups stay correct, because the triggers keep running. Only the
checking and reporting stop.

## Commands

```
sqlflow rollup run     -c rollups.yml [--metrics prometheus]   # the daemon
sqlflow rollup install -c rollups.yml                          # reconcile objects, then exit
sqlflow rollup verify  -c rollups.yml [--since T]              # check stored rows, then exit
sqlflow rollup test    -c rollups.yml --dsn DSN [--tests FILE] [--seed N] [--keep]
sqlflow rollup ddl     -c rollups.yml                          # unchanged
sqlflow rollup serve   -c rollups.yml                          # unchanged
sqlflow rollup check   -c rollups.yml --serve FILE [--migration FILE]
```

- `run` reconciles, backfills, and then checks and reports until SIGTERM.
  `--metrics prometheus` serves `/metrics` and `/healthz` on `:8000`, as
  `sqlflow run` does.
- `install` reconciles and exits. It does not backfill. Entrypoints run it
  after their migrations, so a new grain's table exists before `sqlflow serve`
  prepares the SQL that reads it.
- `verify` runs the verify pass over every bucket since `--since`, default
  all, and exits non-zero on drift. It only reads: it takes no lock and
  never reconciles, so it can run beside the daemon or before one exists.
  `--since` bounds the range because a retention job makes old buckets
  differ from their source by design.
- `test` is described in "`sqlflow rollup test`".
- `ddl` still prints the standalone migration, for a team that applies SQL
  itself. `install` creates the same tables, functions and triggers from the
  same generator code, and backfills differently.
- `check` makes `--migration` optional. A repository that no longer commits
  the migration checks only its serve datasets.

Exit codes are `errs` codes. New ones:

| Code | Meaning |
|---|---|
| `user.config.rollup_change` | The declaration changed in a way that would corrupt stored rows |
| `user.config.rollup_test_failed` | A test case or an invariant failed |
| `system.rollup.drift` | `verify` found stored buckets that differ from the table they are built from |
| `system.rollup.unreachable` | The database refused or dropped the connection |
| `system.rollup.internal` | A database error a rollup command could not classify. The registry gives every domain a catch-all. |

## Configuration

`rollups.yml` gains two top-level blocks. The `rollups` list does not
change, so every file that validates today still validates.

```yaml
# Where the rollup tables live. Only `run`, `install` and `verify` connect.
# ddl, serve, check and test never read it, so a test run cannot reach this
# database.
store:
  type: postgres
  postgres:
    # No default: a daemon without a database fails at startup rather than
    # writing somewhere else.
    dsn: "{{ SQLFLOW_POSTGRES_URI }}"

# The block `sqlflow run` and `sqlflow serve` take.
turbostats:
  id: "{{ SQLFLOW_TURBOSTATS_ID|default('sqlflow-bluesky-rollups') }}"
  report_to: "{{ SQLFLOW_TURBOSTATS_REPORT_TO|default('') }}"
  key: "{{ SQLFLOW_TURBOSTATS_KEY|default('') }}"

rollups:
  - name: posts
    # ...unchanged
```

Rules, reported by `sqlflow validate` and every `rollup` command:

1. `store.type` is `postgres`.
2. `turbostats` follows the rules `run` and `serve` apply to it.

An unset template variable renders as an empty string, so `validate` accepts
an empty `dsn`. `run`, `install` and `verify` refuse one at startup.

Left out on purpose:

- **`strategy`.** v1 has one strategy per store. The key arrives with the
  daemon re-merge strategy and defaults to `trigger` on Postgres, so no v1
  file changes.
- **Intervals and sizes.** v1 observes every 15 seconds, verifies every 60
  seconds, and backfills one source day per chunk. Each becomes a setting
  when a user measures a need for it.
- **A schema key.** Rollup tables and the state table go in the
  connection's `current_schema()`, the first schema on its `search_path`
  that exists. The triggers name tables unqualified, so they resolve them
  through the writer's `search_path`, as today.

## The daemon

The daemon holds two connections: one for the leader lock, and one for its
work.

### The leader lock

The daemon takes `pg_try_advisory_lock(hashtextextended('sqlflow_rollup_leader:' || <rollup name>, 0))`
for every declared rollup on its lock connection. A daemon that gets every
lock is the leader. One that does not is a standby: it retries every observe
interval, and does no other work.

The leader runs `SELECT 1` on the lock connection every observe interval. An
error makes it step down: it stops its work, reconnects, and competes for the
locks again. Render runs the old and the new instance side by side during a
deploy, and the new one takes over when the old one exits.

Nothing the daemon writes depends on the lock for correctness. Two installs
serialize on a transaction lock, a backfill chunk and a write serialize on
the per-bucket locks, and verify only reads.

### The state table

```sql
CREATE TABLE IF NOT EXISTS sqlflow_rollup_state (
  rollup          TEXT        PRIMARY KEY,
  -- The rollup as last applied, without its serve block. Normalized, so key
  -- order and comments never read as a change.
  declaration     JSONB       NOT NULL,
  sqlflow_version TEXT        NOT NULL,
  applied_at      TIMESTAMPTZ NOT NULL,
  -- Per table being filled: the start of the oldest source day done so far.
  -- A table leaves the object when its backfill completes.
  backfill        JSONB       NOT NULL DEFAULT '{}',
  -- Tables a later declaration removed, each with the set, grain and from
  -- that built it. Their triggers still run, verify still checks them, and
  -- a pending backfill stays pending.
  retained        JSONB       NOT NULL DEFAULT '[]'
);
```

The name is fixed, so every version of `install` and `run` finds it.

### Reconcile

`install` runs these steps, and `run` runs them at startup. All of them run
in one transaction, because Postgres DDL is transactional:

1. Take `pg_advisory_xact_lock(hashtextextended('sqlflow_rollup_install', 0))`.
   Every entrypoint of a deploy can run `install` at once, and the later ones
   find nothing to do.
2. Check each source. It must exist and have the time column and every
   column the declaration reads. An index must lead with the time column:
   the trigger on the source reads it by a time range on every write, and
   without the index each write scans the whole history. The error names the
   `CREATE INDEX` statement to run.
3. Compare the declaration with the state row, and classify every difference.
4. Compare each existing table with the columns it should have. The daemon
   creates a temporary table from the generator's query `WITH NO DATA`, which
   is how `ddl` takes column types without connecting, and compares names and
   types. A mismatch stops the daemon.
5. Apply the declaration: `CREATE TABLE IF NOT EXISTS` and its unique index,
   `CREATE OR REPLACE FUNCTION`, and `CREATE OR REPLACE TRIGGER`, from the
   generator code `ddl` uses.
6. Record the declaration and the SQLFlow version. Mark the backfill targets.

Before any DDL, the transaction locks each source `IN SHARE ROW EXCLUSIVE
MODE`, in the order a writer reaches them. A writer's statement locks the
source, then its triggers lock the rollup tables. `CREATE UNIQUE INDEX IF
NOT EXISTS` locks a rollup table even when the index exists, so an install
that reached the tables first deadlocked beside a live writer in 34 of 40
runs, measured in review on 2026-09-25.

A source that another declared rollup builds, such as a rollup that reads
another's hourly table, is written only by that rollup's triggers, so it is
locked after that rollup's source. Name order breaks ties. Install cannot
see a foreign trigger chain, such as the Render template's writers table
feeding `metrics_1m`, so two declared sources that such a chain writes keep
name order, and an install beside that writer may cost a retry.

While install waits for a source, the pipeline's next writes queue behind
it. `lock_timeout`, 2 seconds, bounds each wait, and install retries three
times on a lock timeout or a deadlock before it fails. The timeout is set
after the install lock, because it bounds an advisory lock's wait too. The
lock is held for the DDL only, never for a backfill.

The transaction runs in READ COMMITTED whatever the database's default. The
install lock serializes installs only because each statement after it takes
a new snapshot and reads the previous install's commit.

| Difference | Action |
|---|---|
| A new rollup, grain or dimension set | Create its tables and triggers. Mark it for backfill. |
| A new SQLFlow version | Replace every function and trigger. The tables do not change. |
| A removed rollup, grain or dimension set | Keep its tables and triggers. Log a warning that names them. Move them to `retained` with the set, grain and from that built them. A backfill still pending stays pending. |
| A changed measure type, dimension list, grain `from`, or source table, time column or grain | Stop with `user.config.rollup_change` and the YAML path. |
| An added or removed source dimension | Nothing. No generated table or trigger reads `source.dimensions`; only the file's rules and serve do. |
| A measure added to or removed from an existing dimension set | Stop with `user.config.rollup_change`. A removed measure's column would go stale in every stored row. Declare a new dimension set instead. |
| A retained table that no longer exists | Remove its record and its pending backfill, and report it. Declared again, it is a new table and fills. |
| A declared table that is in `retained` | Move it back when its set and grain match the ones retained, and stop with `user.config.rollup_change` when they differ: its rows were merged the old way. Its triggers never stopped, so it needs no new backfill, and one still pending stays pending. |

Backfill targets are the new tables built from the source, or from a table
whose backfill is complete. Their upserts fire the triggers that fill every
new table above them, as the migration's backfill does today.

### Taking over existing objects

`0005_rollups.sql` created tables, functions and triggers with the names the
daemon generates. A database with those objects and no state row is adopted:

1. Step 4 checks every existing table's columns.
2. Step 5 replaces the functions and triggers with the daemon's, which
   differ from `0005`'s only when the generator changed after it was
   generated.
3. The tables built from the source are marked for backfill. Upserts are
   idempotent, so backfilling filled tables rewrites the same values.

### Backfill

The leader fills each target in chunks:

- A chunk covers at most one UTC day of source buckets. The first chunk is
  in the day of the source's newest bucket, and the last is in the day of
  its oldest, so recent history is right first.
- A chunk takes at most 1,000 advisory locks. The planner counts the buckets
  a chunk touches at every grain of every dimension set, and halves the chunk
  until the count fits. The default lock table holds 6,400 locks for the
  whole server, and a chunk shares it with the pipeline's writes.
- A chunk re-merges at most 100,000 rows of the table its target is built
  from. A write to any of the chunk's buckets waits for the whole chunk, and
  the chunk's time grows with its rows: a day of 1,000 languages by the
  minute, 1.44 million rows, took 3.5 s, and blocked a write for 3.3 s. The
  sink gives a write 10 s. The planner walks back from the chunk's newest
  row to the first row past the budget, reading at most the budget, and
  halves the chunk until that row falls outside it, down to one bucket of
  the target. Measured on 2026-09-25 at 1,000 languages: chunks of 90
  minutes, the longest 313 ms, and a write beside them waited at most
  277 ms.
- Each chunk is one READ COMMITTED transaction. It takes the install lock
  shared, so it never runs beside an install that is changing its table,
  and sets `lock_timeout` as install does. It reads which of the target's
  buckets its rows fall in, and re-merges exactly those from the table the
  target is built from, so a bucket that appears after the read stays with
  the write that made it, whose trigger holds its lock. It records its
  progress in the state row, and only over the entry it read. When an
  install or another chunk changed the entry, the chunk rolls back and the
  daemon reads the entries again. Progress written over an entry an install
  reset would skip the history a re-created table lacks.
- Before it re-merges, a chunk waits in line for the rollup's lock, up to
  1 s, which every trigger its upserts fire takes first. It holds only the
  install lock, shared, which no writer waits for, and Postgres serves a
  waiter before writers that ask later, so writers flushing back to back
  cannot starve it. Then it takes every lock its buckets need: each target
  bucket's, and each coarser bucket's its upserts cascade to, with
  `pg_try_advisory_xact_lock`, in one round trip. When a write holds any of
  them, the chunk rolls back, which releases the rest, and tries again after
  50 ms, 20 times, before it reports the chunk busy. The daemon then fills
  the other pending tables and tries the busy one last, so a write left
  open on one table's bucket holds up that table only. When every pending
  table is busy, it waits an interval. The coarser triggers the upsert
  fires then take locks the chunk already holds, and return at once.
- A chunk never waits while it holds a lock. An upsert fires each rollup
  trigger twice, for its inserted and its updated rows, and the two passes
  lock buckets in different orders, so a chunk that waited holding locks in
  bucket order deadlocked a single live writer in 1 run of 3, measured on
  2026-09-25. A chunk that never waits cannot be one side of a deadlock, and
  a write waits on a chunk for the chunk's duration at most, which the row
  budget bounds.
- The last chunk is the one that reaches the source's oldest row, binned to
  the width of the rows the target is built from, so a day built from
  6-hour rows includes the 6-hour row that holds the source's first minute.

No write is lost. The triggers exist before the first chunk, so every write
after `install` re-merges its own buckets in its own transaction. A chunk and
a write on the same bucket serialize on the bucket's lock, and in READ
COMMITTED the later one reads the earlier one's commit. This is the argument
the 2026-09-15 spec measured for two overlapping writers. A bucket wider
than a chunk, such as a week, re-merges on every chunk it spans. The last of
those re-merges reads every child.

The chunked backfill does not set `sqlflow.rollup_backfill`, so the triggers
it fires take their locks, which the chunk already holds.

Writers to one rollup take turns. Every generated trigger takes the
rollup's lock, `sqlflow_rollup:<name>`, before its buckets'. Without it,
writers whose statements span several buckets deadlock, because each
statement's two passes lock buckets in different orders. On 2026-09-25,
four writers upserting 20 random minutes over three days through the
Postgres sink deadlocked on 38 of 160 flushes. With the lock, none did.

The trigger takes the lock after its statement has written the source rows.
That is safe while each writer transaction writes the source in one
statement, as the Postgres sink does. A transaction that writes the source
twice can hold the lock from its first statement while its second waits for
another writer's row.

The lock costs no throughput, because the bucket locks already made writers
to one bucket take turns. The work each flush does is the limit: a trigger
re-merges whole buckets, all dimension values of every touched bucket, so a
flush costs about the same however few rows it wrote, and each writer pays
it again. Measured on 2026-09-25 on a laptop, replaying 20 minutes back to
back, each writer flushing its share of the customers for every minute plus
a 10% late re-flush three minutes back:

| Customers | Writers | Minutes of data per second | Flush p50 | Flush max | Failed with the lock | Failed without it |
|---|---|---|---|---|---|---|
| 1,000 | 1 | 10.5 | 88 ms | 139 ms | 0 of 20 | 0 of 20 |
| 1,000 | 2 | 4.0 | 255 ms | 398 ms | 0 of 40 | 3 of 40, deadlocked |
| 1,000 | 4 | 1.5 | 701 ms | 1.1 s | 0 of 80 | 10 of 80, deadlocked |
| 10,000 | 1 | 1.2 | 903 ms | 1.0 s | 0 of 20 | 0 of 20 |
| 10,000 | 2 | 0.5 | 2.2 s | 3.4 s | 0 of 40 | 3 of 40, deadlocked |
| 10,000 | 4 | 0.2 | 5.9 s | 10.0 s | 4 of 80, timed out | 12 of 80 deadlocked, 6 timed out |

Live, a writer flushes once a minute, which needs 0.017 minutes of data per
second, so every row keeps up. A backlog replay at 10,000 customers and four
writers reaches the sink's 10 s flush timeout, with or without the lock.
More writers per rollup make the merge slower, not faster. The daemon
re-merge strategy in the follow-ups merges each bucket once per pass
instead of once per flush.

### The loop

The leader runs two passes:

- **Observe**, every 15 seconds: read each table's newest bucket through its
  unique index, and the source's through the index step 2 requires. Record
  freshness and completeness.
- **Verify**, every 60 seconds: check the newest two buckets of every table,
  which are the open bucket and the one that closed before it.

### Verify

Verify recomputes a table's rows over a range of buckets from the table it
is built from, using each measure's merge, or its source expression when the
table is built from the source. It compares the result with the stored rows
through a full outer join on the table's key.

- **One statement, one snapshot.** A writer's transaction writes the source
  and every grain above it, so one snapshot sees all of a write or none of
  it. The comparison is exact even for the open bucket.
- **Comparison.** Integers, text and timestamps compare with
  `IS DISTINCT FROM`. `double precision` compares within a relative 1e-9,
  because Postgres sums floats in no fixed order and exact equality would
  report drift on correct rows.
- **Drift** is a table and a bucket with at least one differing, missing or
  extra row. A table whose newest bucket trails the source's is drift too:
  the recomputed row exists and the stored one does not.
- **Each edge is checked alone.** A table is compared with the table it is
  built from, never with the source, so a report names the broken edge.
- **Rows pair on the table's key through `GROUP BY`** over both sides, not a
  full join. Postgres refuses a full join on `IS NOT DISTINCT FROM`, and
  grouping treats `NULL` dimension values as equal, as the unique index
  does.
- **A table still filling is skipped**, with every table its chunks'
  upserts reach. It differs from its source by design until the fill
  completes, and checking it would report `degraded` during every backfill.

The loop checks the newest two buckets of every table. The newest is the
later of the table's newest and the newest its from table makes, so a table
whose trigger stopped is checked where it trails. `sqlflow rollup verify`
checks every bucket since `--since`, a day of whole buckets per statement.

### Shutdown

On SIGTERM the daemon finishes the open chunk or pass, releases its locks,
and exits 0.

### Failure behavior

| Failure | Result |
|---|---|
| The daemon is down | The rollups stay correct. Checking and reporting stop, and TurboStats shows the instance silent. |
| Reconcile fails | The daemon exits non-zero with its code. A supervisor's restart loop makes it visible. |
| The database is unreachable | The daemon retries. `/healthz` reports `failed` after three observe intervals. |
| A backfill chunk fails | The chunk rolls back and retries on the next observe interval. Progress is saved per chunk. |
| Verify finds drift | The daemon counts and logs it, and keeps running. A restart cannot fix drift. |

## Observability

### Freshness

The freshness of a table is the time from the end of its newest bucket to
when it was observed. A bucket's end is its start plus the table's grain.

It is output-side: it measures where the data landed, not what the pipeline
received. For the source table it is the pipeline's output freshness, and it
catches a pipeline that runs and writes nothing. For a rollup table it should
equal the source's, binned to the table's grain. A table that trails is drift.

The measurement is a package of its own, `internal/freshness`. It takes a
store connection, a table, a time column and a grain, and knows nothing
about rollups. The daemon is its first user, and `sqlflow monitor` can be
the second without a redesign.

### Store identity

Control shows a table's freshness apart from the process that reported it,
so every reporter must name one table the same way. Two services can reach
one database through two hostnames, such as Render's private and external
URLs, so the DSN cannot be the name. It also carries credentials.

`store_id` is `pg:` and the first 16 hex characters of
`sha256(system_identifier || '/' || current_database())`, where
`system_identifier` comes from `pg_control_system()`. It is the same for
every reporter and carries no hostname or credentials. Checked on Postgres
18.6 on 2026-09-24: a role that is neither superuser nor a member of any
monitoring role reads `pg_control_system()`.

A server that refuses the function gets `sha256(coalesce(host(inet_server_addr()), 'local') || ':' || inet_server_port() || '/' || current_database())`,
and `store_id_kind: address`, which tells Control the id may not match
another reporter's. The build checks Render's managed Postgres first.

### Completeness

Completeness is reported for dimension sets that declare `count_buckets`,
and for no other. For the newest closed bucket at each grain, the daemon
reads one stored row: the source buckets present, and the number expected,
which is the grain's width over the source grain. For the demo that reads
"57 of 60 minutes" for the last hour. Completeness never changes health,
because a sparse source has real gaps.

### Trigger cost

The triggers run in the writer's transaction, so their cost is already part
of the pipeline's `sink_flush` duration. When `track_functions` is `pl` or
`all`, the daemon also reports each trigger function's calls and total time
from `pg_stat_user_functions`. Only a superuser, or a role granted `SET` on
it, can set `track_functions`, so these fields are optional.

### Metrics

OTel instruments with flat names, as serve's newer instruments are. The
Prometheus exporter appends the unit and `_total`. The labels are `rollup`
and `table`.

| Instrument | Kind | Meaning |
|---|---|---|
| `rollup_verify_buckets` | counter | Buckets recomputed and compared |
| `rollup_drift_buckets` | counter | Buckets that differed |
| `rollup_backfill_buckets` | counter | Buckets written by backfill |
| `rollup_backfill_busy` | counter | Chunks that gave up because a write held one of their buckets on every try |
| `rollup_backfill_chunk_duration` | histogram, s | One chunk's transaction |
| `rollup_verify_duration` | histogram, s | One verify pass |
| `rollup_errors` | counter, and `phase`: install, backfill, verify, observe, lock | Errors by phase |
| `rollup_leader_acquired` | counter | Times this process became the leader |
| `rollup_newest_bucket_timestamp` | gauge, s | The newest bucket of each table and of the source |

### `/healthz`

The rules `sqlflow run` uses: 200 means do not restart, and 503 means
restart. The first matching rule wins.

| Status | Code | When |
|---|---|---|
| `failed` | 503 | Reconcile failed, or the database was unreachable for three observe intervals |
| `degraded` | 200 | The last verify pass found drift |
| `standby` | 200 | Another instance holds the leader lock |
| `backfilling` | 200 | A backfill is running. The reason names the tables left and the source history left in the one filling. |
| `starting` | 200 | The process is installing and taking the leader lock, or it leads and has not yet read which tables need filling. Before that read, no pending tables means unknown, not none. |
| `healthy` | 200 | None of the above |

### TurboStats

Two additions to the bundle. Both are optional, so the document stays at
version 1.

A top-level `freshness` list, which any process can report:

```json
"freshness": [
  {
    "store": "postgres",
    "store_id": "pg:3f9a0c1d2e4b5a6f",
    "store_id_kind": "system",
    "table": "public.posts_by_lang_1h",
    "time_column": "bucket",
    "grain_seconds": 3600,
    "newest_bucket_at": "2026-09-24T19:00:00Z",
    "observed_at": "2026-09-24T19:41:37Z"
  }
]
```

- Control joins entries on `store_id` and `table`, and the newest
  `observed_at` wins.
- `observed_at` tells a stale reporter apart from stale data, as
  `event_lag_observed_at` does for a pipeline's event lag.
- `newest_bucket_at` is absent for an empty table.
- The leader reports one entry per rollup table and one for each source. A
  standby reports none.

A `rollup` section, whose presence says the process runs rollups:

```json
"rollup": {
  "role": "leader",
  "rollups": [
    {
      "name": "posts",
      "strategy": "trigger",
      "backfill": {"days_done": 4, "days_total": 10},
      "verify_bucket_count": 5400,
      "drift_bucket_count": 0,
      "completeness": [
        {"table": "posts_total_1h", "bucket_at": "2026-09-24T18:00:00Z",
         "source_buckets": 57, "expected_buckets": 60}
      ],
      "triggers": [
        {"function": "sqlflow_rollup_posts_by_lang_5m", "calls": 1440, "total_seconds": 3.2}
      ]
    }
  ],
  "last_error_code": "system.rollup.unreachable",
  "last_error_at": "2026-09-24T19:40:02Z"
}
```

- `backfill` is absent once every table is filled.
- `completeness` is absent for a rollup with no `count_buckets` measure.
- `triggers` is absent unless `track_functions` is on.
- The counts are the instruments' totals since the process started.
- A standby reports `role` and nothing else.

The shape is guarded twice: the Go type walk in `turbostats/wire`, and
`pytest tests/release`. Control's view of both additions belongs to the
control repository.

### Logs

One line for each:

- An object created or replaced, and a table moved to `retained`.
- Backfill start, each day done, and finish.
- Leader acquired, leader lost, and standby.
- A drifted bucket: the table, the bucket, the first differing measure, and
  the stored and recomputed values. Limited to 10 lines per table per pass.

## `sqlflow rollup test`

```
sqlflow rollup test -c rollups.yml --dsn "$TEST_DSN" [--tests rollups.test.yml] [--seed N] [--keep]
```

`--dsn` names a Postgres where the team's migrations have run, so the source
tables exist. The role needs `CREATE` on the database. The command:

1. Creates a schema, `sqlflow_test_<random>`.
2. Clones each source into it with
   `CREATE TABLE ... (LIKE <source> INCLUDING DEFAULTS INCLUDING IDENTITY INCLUDING GENERATED INCLUDING INDEXES)`.
   The clone keeps the columns, `NOT NULL`, defaults, and the primary key. It
   leaves out `CHECK` constraints, so a generated value never fails a rule the
   rollups do not depend on. The Render template's `metrics_1m` has one.
3. Sets `search_path` to the schema, and runs `install`'s reconcile there.
4. Runs the generated workload and the fixture cases.
5. Drops the schema, unless `--keep` is set.

The command never reads `store.postgres.dsn`, so it cannot reach the
database the daemon runs against.

### Invariants

Checked on every case's final state, with no expectations written:

1. Every table equals a from-scratch `GROUP BY` of the source at the table's
   own width, using each measure's source expression.
2. Every bucket lies on its grain's UTC boundary.

The comparison rules are verify's.

### The generated workload

Without `--tests`, the command writes to each source for each rollup:

- 20 batches of up to 50 rows, over three days that include 2026-03-08, a US
  daylight saving change.
- One row in ten rewrites an earlier row's key, as a republished minute does.
- Each batch comes from a session whose `TimeZone` is `UTC`,
  `America/New_York` or `Asia/Kolkata`.
- Values follow each column's type: integers from 0 to 1,000, doubles with
  fractions from -1,000 to 1,000, text from a pool of five values, and
  timestamps inside the row's bucket. `NULL` appears only in nullable
  dimension columns.

It checks the invariants and prints the seed. `--seed` reproduces a run. A
column type the generator cannot produce stops the run with the column's
name and type. It never skips the column.

This is what makes a model-written `rollups.yml` checkable without fixtures.

### Fixture cases

Fixture cases check what the invariants cannot see, such as `last`,
`count_buckets`, and the totals a customer expects:

```yaml
# rollups.test.yml
tests:
  - name: a republished minute replaces its count at every grain
    rollup: posts
    # Each write is one statement in its own transaction, in the sink's
    # upsert shape: ON CONFLICT on the time column and source.dimensions.
    writes:
      - [{bucket: "2026-09-24T12:07:00Z", lang: en, posts: 5}]
      - [{bucket: "2026-09-24T12:07:00Z", lang: en, posts: 9}]
    # A listed table must hold exactly these rows, every column of each.
    # Unlisted tables are checked by the invariants only.
    expect:
      posts_by_lang_5m:
        - {bucket: "2026-09-24T12:05:00Z", lang: en, posts: 9}
      posts_total_1h:
        - {bucket: "2026-09-24T12:00:00Z", posts: 9, minutes: 1}
```

Each case starts from empty tables. Values bind as text cast to each
column's type. A failure prints the case, the table, the key, and the
expected and actual rows, and the command exits with
`user.config.rollup_test_failed`.

Rules, each reported with its YAML path: `rollup` names a declared rollup,
every written key is a source column, every `expect` table is one of the
rollup's tables, and every expected row names every column of its table.

## Rollout

### Engine

One PR each, every one opened against main, in this order:

1. `internal/freshness` and the store identity.
2. The state table, the reconcile planner, and `install`.
3. Chunked backfill.
4. `run`: the leader lock, the loop, `/healthz`, and metrics.

The Postgres sink does not change: the trigger strategy needs no change

### The Bluesky demo

On a fresh database, `0006` creates a view that reads `posts_total_1d`, so
the rollup tables must exist before it runs. The demo changes:

- `migrations/0005_rollups.sql` becomes a step that runs
  `sqlflow rollup install`, and `bin/migrate.sh` learns to run it. Its
  version stays `0005_rollups`, so production, which applied it, skips it,
  and a fresh database gets the tables before `0006`.
- `bin/serve.sh` runs `sqlflow rollup install` before `sqlflow serve`.
- The Dockerfile copies `rollups.yml`.
- `rollups.yml` gains `store` and `turbostats`. `rollups.test.yml` is new.
- CI runs `make migrate`, `sqlflow rollup test`, and
  `sqlflow rollup check --serve serve.yml`.
- `render.yaml` gains a worker, `sqlflow-bluesky-rollups`, that runs
  `sqlflow rollup run` on the smallest plan.

### The parity proof

On the production demo database:

1. Before adoption, run `sqlflow rollup verify` over the full history. The
   demo never deletes, so every bucket is in range.
2. Deploy the daemon. It adopts the `0005` objects and backfills with no
   table lock.
3. For 24 hours:
   - `rollup_drift_buckets` stays 0 for every table.
   - The source's freshness tracks the pipeline.
   - The pipeline's `sink_flush` duration does not change during the
     backfill.
   - TurboStats shows the daemon's memory flat.
4. Run `sqlflow rollup verify` over the full history again. It reports no
   drift.

### The Render template

The template in this repository changes the same way: `0003_rollups.sql`

## What breaks if this is wrong

| If | Then | Caught by |
|---|---|---|
| Install locks a rollup table before its source | Install deadlocks beside a live writer and fails the deploy | `InstallBesideAWriterMidTransaction` |
| Install locks sources by name when one rollup reads another's table | A deadlock per install beside a live writer, which the retry hides | `InstallBesideAWriterWhenOneRollupReadsAnother`, which asserts one attempt |
| A retained table's record outlives the table | Declaring the set again in a new shape is refused over rows that no longer exist | `ARetainedTableDroppedByHandCanBeDeclaredAgain` |
| Install waits for a source without a bound | A transaction left open stalls the install and every pipeline write queued behind it | `InstallGivesUpOnALockRatherThanStallThePipeline` |
| A retained table keeps only its name | Declaring it again in another shape mixes two kinds of row in one table, and a rollback and roll-forward drops its pending backfill | `ARetainedSetDeclaredAgainInAnotherShapeIsRefused`, `ARollbackAndRollForwardKeepAPendingBackfill` |
| Backfill runs before the triggers exist | A write between the backfill's read and the trigger's creation never reaches the coarse grains | `ChunkedBackfillLosesNoConcurrentWrite` |
| Backfill skips the bucket locks | A chunk and a write each re-merge from a snapshot missing the other, and the later commit overwrites the earlier one | `ABackfillChunkNeedsItsBucketLock`, which fails without the chunk's own keys |
| A trigger locks its buckets without the rollup's lock first | Writers whose flushes span several buckets deadlock, 38 of 160 flushes from four writers | `ConcurrentWritersNeverDeadlock` |
| A chunk skips the rollup's lock | Its upserts' triggers wait for the lock while the chunk holds its bucket locks | `ABackfillChunkNeedsTheRollupsLock` |
| A chunk tries the rollup's lock rather than waiting in line | Writers flushing back to back starve the backfill | `ChunkedBackfillLosesNoConcurrentWrite`, with four writers |
| A chunk waits while it holds bucket locks | A writer's two trigger passes deadlock with it, and either side can lose | `ABackfillChunkNeverWaitsHoldingALock`, which fails with 55P03 against blocking locks |
| A chunk outgrows the lock table | `out of shared memory`, and the backfill stops | The chunk planner's unit test at a 1s source grain |
| A chunk's rows have no bound | A write waits seconds on the chunk, past the sink's 10 s at a few thousand dimension values, and the pipeline stops | `ABackfillChunkFitsTheRowBudget` |
| A busy table stays first in line | A write left open on one table's bucket stops every other table's backfill | `ABusyTableHoldsUpNoOther` |
| A chunk writes progress over an entry that moved | An install re-creates a table, and a chunk begun before it skips the history the new table lacks | `AChunkWritesNoProgressOverAMovedEntry` |
| Adoption misreads an existing table | A trigger writes into a mismatched column, the pipeline's write fails, and the worker restart-loops | `AdoptionRefusesAMismatchedTable` |
| Verify reads across two snapshots | Drift reported on correct rows, and `/healthz` stuck at `degraded` | `VerifyUnderConcurrentWritesReportsNoDrift` |
| Verify compares doubles exactly | The same, for every `numeric: double` sum: compared exactly, 4 of 12 correct buckets read as drift on 2026-09-25, because the trigger and the recompute sum in different orders | `ANullDimensionAndADoubleSumVerifyClean`, `OnlyADoubleSumMatchesWithinATolerance` |
| Verify pairs rows on `=` | A `NULL` dimension value reads as a missing row and an extra one | `ANullDimensionAndADoubleSumVerifyClean` |
| Verify checks a table still filling | `/healthz` reports `degraded` during every backfill | `VerifySkipsTablesStillFilling` |
| A new leader reports before it reads its tables to fill | `/healthz` says `healthy` over empty tables, and a deploy check passes | `TheDaemonInstallsAndFillsHistory`, which fails once the verify pass widens that window |
| Reconcile refuses a removal | A rollback fails every entrypoint that runs `install`, and the API goes down | `ReconcileKeepsRemovedTables` |
| `store_id` differs between reporters | Control shows one table twice, each half as fresh | `OneStoreIDForTwoHostnames` |
| The test clone keeps `CHECK` constraints | The generated workload fails on a correct declaration | `RollupTestCommand` on the Render template's `metrics_1m` |

## Follow-ups

- **The daemon re-merge strategy.** For raw events, where many statements
  write one bucket and a statement trigger re-reads the bucket on each one.
  Measured on Postgres 18.6 on 2026-09-24:
  - A column `sqlflow_xid xid8 NOT NULL DEFAULT pg_current_xact_id()` is
    stamped on insert. An upsert with `SET sqlflow_xid = DEFAULT` re-stamps
    it, and `updated_at` keeps the first write. A btree index serves the
    range read.
  - A cursor at the highest xid seen loses rows. Writer A took xid 758 and
    held its transaction open. Writer B took 759 and committed. The cursor
    moved to 759, and A's row was never read after A committed.
  - A cursor that reads `[cursor, pg_snapshot_xmin(pg_current_snapshot()))`
    loses none. It waited at 758 while A was open, and then read A and B.
  - Only a transaction that has written holds the horizon. A stuck writer
    causes lag, never loss, and `pg_stat_activity.backend_xid` names it.

  The Postgres sink gains an option to re-stamp the column on upsert.
- **ClickHouse incremental materialized views.** They fire on insert and
  never see an update, so a republished minute adds twice. The source must be
  insert-only, and a retried batch must carry the same
  `insert_deduplication_token`. The SQLFlow ClickHouse sink sends no token
  today.
- **`sqlflow monitor`**, a process that reports the `freshness` list for
  tables no daemon manages.
- **Control's freshness view**, which reads the `freshness` list by store and
  table.
- **`sqlflow rollup drop`**, to remove a retained table and its triggers on
  purpose.
- **Renaming `sqlflow rollup serve`**, whose name collides with
  `sqlflow serve`, or having serve read `rollups.yml` directly.
